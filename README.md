# Agent Operations — ข้อมูลจริงเท่านั้น

ศูนย์ติดตามการทำงาน Agent สำหรับสำนักงานวิชาการ มหาวิทยาลัยศรีปทุม

## สถานะที่ตรวจสอบแล้ว

สร้างที่เก็บ RUN_LOG และ API บน Supabase ของโครงการ `hr-agent-digital-hub` แล้ว โดยใช้ schema `agent_ops` แยกจากตารางธุรกิจ HR ไม่ได้ย้ายข้อมูล HR มารวม ไม่ได้ลบทะเบียนเดิม และไม่ได้เติม Agent, Skill, mapping, ประวัติงาน หรือบัญชีผู้ใช้เพื่อให้หน้ารายงานมีข้อมูล

ผลตรวจฐานข้อมูล ณ **19 กันยายน 2026 เวลา 19:11 น. ประเทศไทย**:

- RUN_LOG ใน `agent_ops.operation_runs`: **0 รายการ**
- เหตุการณ์เดิมใน `agent_ops.execution_events`: **0 รายการ**
- สมาชิก Workspace ที่ active: **0 บัญชี**
- Agent และ Skill ที่ผ่านเงื่อนไขยืนยันการสร้างของหน้าปฏิบัติการ: **0 รายการ**

ศูนย์ในทะเบียนที่ยืนยันแล้วไม่ได้แปลว่าองค์กรไม่มี Agent แต่หมายความว่ายังไม่มีรายการที่ผ่านเงื่อนไขใหม่นี้ รายการเดิมที่เป็นร่าง/ข้อเสนอ/ยังไม่ยืนยันยังอยู่ในฐานข้อมูล แต่ไม่ถูกนำมานับเป็นสิ่งที่สร้างแล้ว หลักฐานและคำสั่งตรวจอยู่ใน `verification-receipt.json` และ `sql/verify.sql`

## เปิดใช้หน้าเว็บ

เปิด `Agent-Operations-Real.html` แล้วกด **เข้าสู่ระบบ** ด้วยบัญชี Supabase Auth ของโครงการที่มีอยู่แล้ว บัญชีนั้นต้องเป็นสมาชิก active ของ Workspace `agent-factory` ด้วย การมีบัญชีในระบบ HR ไม่ได้ทำให้ได้รับสิทธิ์ Agent Operations โดยอัตโนมัติ

**ยังต้องระบุบัญชีอีเมลจริงที่จะเป็นผู้ดูแลก่อนเปิดสิทธิ์ครั้งแรก** รุ่นนี้ไม่สร้างบัญชี ไม่สมัครสมาชิกให้เอง และไม่เปิดข้อมูลให้บุคคลทั่วไปอ่านได้ ผู้ดูแลฐานข้อมูลต้องเพิ่ม membership ให้บัญชีที่เจ้าของงานอนุมัติ ไม่ควรส่งรหัสผ่านหรือ secret key ผ่านแชท

เมื่อยังไม่ล็อกอิน หรือยังอ่านฐานข้อมูลไม่ได้ ตัวชี้วัดแสดง `—` พร้อมสถานะที่ชัดเจน เมื่ออ่านสำเร็จแต่ไม่มีแถว จำนวนงานเป็น 0 แต่อัตราสำเร็จ เวลาเฉลี่ย/มัธยฐาน และคอขวดที่ยังคำนวณไม่ได้ไม่ถูกแต่งขึ้น การขาดข้อมูลไม่ได้หมายถึง Agent ทำงานล้มเหลว

หน้าเว็บใช้ธีมสว่างเป็นค่าเริ่มต้น รองรับมือถือ 390px ธีมมืด คีย์บอร์ด และ reduced motion ไม่มีข้อมูลจำลอง ไม่มีตัวสร้างข้อมูล ไม่มี fallback ที่สร้างประวัติ 90 วัน และไม่มีไฟล์ฟอนต์แนบมา

## ขอบเขตที่พร้อมและที่ยังไม่เปิดใช้

**ทำแล้ว:** ตารางเก็บงาน, API อ่าน/เขียน/ลงทะเบียน, สิทธิ์ระดับ Workspace, หน้าเว็บที่ตั้งค่าเชื่อม API จริง, การนำเข้าและบันทึกด้วยมือสำหรับผู้มีสิทธิ์, ชุด schema และ client สำหรับให้ runtime ส่งงานที่เกิดจริง

**ยังไม่ทำ:** เปิดสิทธิ์บัญชีทีม, ยืนยัน Agent/Skill ที่สร้างจริงทีละรายการ, ติดตั้งตัวจับเวลาและตัวส่ง RUN_LOG ใน runtime ของ Agent, ทดสอบการล็อกอินและเขียนงานจริงด้วยบัญชีทีม และเผยแพร่ HTML เป็นเว็บไซต์กลางของทีม ไฟล์ดาวน์โหลดนี้ไม่ใช่หลักฐานว่ามีลิงก์กลางออนไลน์แล้ว

ไม่มีการเริ่ม Agent, สั่งทำงานเบื้องหลัง, สร้างงานย้อนหลัง หรือเชื่อมโมเดล AI ให้เอง การมีที่เก็บข้อมูลไม่เท่ากับมี runtime ส่งข้อมูลมาแล้ว

## การลงทะเบียนโดยไม่สร้างข้อมูลสมมติ

ใช้ `agent-registry.schema.json` เป็นข้อกำหนดรูปแบบ ไม่ใช่ชุดข้อมูลตัวอย่าง ผู้ดูแลนำเข้าเฉพาะ Agent/Skill ที่ตรวจแล้วว่ามี implementation จริง โดยระบุ `confirmedCreated: true`, `version` และ `implementationEvidence` ที่ชี้หลักฐานจริง เช่น ที่ตั้งไฟล์ definition หรือที่ตั้งโค้ด โดยไม่ใส่ secret หรือข้อมูลส่วนบุคคล

การยืนยันนี้คือคำรับรองของผู้ดูแล ไม่ใช่การตรวจโค้ดอัตโนมัติ และไม่ยืนยันว่า Agent รันสำเร็จหรือเชื่อมต่อ runtime แล้ว ระบบไม่เดาว่า Agent ใดเป็น Orchestrator จากชื่อ ต้องระบุ `isOrchestrator` เองตามจริง

API อัปเดตเฉพาะรายการที่ส่งเข้ามา ไม่ลบรายการอื่น ทักษะที่อ้างใน mapping ต้องมี implementation ที่ยืนยันแล้ว หากยังไม่มีจะปฏิเสธ ไม่สร้าง placeholder ให้ รายการที่มีเพียงแนวคิดไม่ต้องส่งเข้าทะเบียนปฏิบัติการ

## การรับงานจริง

เก็บ `RUN_LOG` หนึ่งก้อนต่อหนึ่งงานที่จบแล้วตาม `RUN_LOG.schema.json` มี 3 แหล่งที่มา:

- `runtime`: ระบบหลังบ้านส่งค่าที่วัดได้จริง ใช้สิทธิ์ฝั่ง server เท่านั้น
- `manual`: คนบันทึกผลและเวลาของงานที่เกิดจริง ต้องเป็น editor/admin
- `import`: นำเข้าไฟล์/ข้อความที่เป็นบันทึกจริง ต้องเป็น editor/admin

หน้าเว็บไม่มีการกรอกเวลา ผลลัพธ์ หรือขั้นตอนสำเร็จให้ล่วงหน้า ขั้นตอนใดไม่เกิดไม่ต้องเลือก ห้ามให้โมเดลเดาเวลา หากยังไม่มีตัวจับเวลาให้เตรียม instrumentation ก่อน ไม่กรอก 0 เพื่อทดแทนค่าที่ไม่ทราบ

รหัส Agent/Skill ที่ไม่อยู่ในทะเบียนสามารถปรากฏเป็นรายการนอกทะเบียนจาก RUN_LOG จริงได้ แต่จะไม่สร้าง Agent/Skill เพิ่มให้โดยอัตโนมัติ

ข้อมูลเป็น append-only: `runId` เดิมและข้อมูลเหมือนเดิมข้ามซ้ำ; ข้อมูลขัดกันปฏิเสธ ไม่เขียนทับ และไม่มีปุ่มลบชุดประวัติจากหน้าเว็บ หากบันทึกผิดต้องให้ผู้ดูแลตรวจและกำหนดวิธีแก้ที่รักษาประวัติ ไม่แก้ผลเก่าเงียบ ๆ

## นิยามและข้อจำกัดของตัวเลข

นับงานตาม `runId` ไม่ซ้ำและกรอง `startedAt` ย้อนหลัง 7/30/90 วันหรือทั้งหมด อัตราสำเร็จคือ success หารงานทุกสถานะ; non-success รวม failed, escalated และ abandoned ไม่ใช่ failed เพียงอย่างเดียว

หนึ่ง step ที่มี `skillId` นับหนึ่งการเรียก ไม่เพิ่มตามจำนวน retries อัตราปัญหา Skill ใช้ step ที่ fail หรือ retry หาร step ของ Skill นั้น

เวลางานประมาณจากผลรวม `durationSec × (1 + retries) + waitSec` โดย durationSec เป็นเวลาต่อ attempt ไม่รวมรอ ไม่ใช่ wall-clock และอาจสูงกว่าจริงเมื่อทำงานขนาน งานที่ไม่มี step ไม่ถูกตีความว่ามีเวลาทำงาน 0 วินาที มัธยฐานใช้เฉพาะงานที่มีค่าประมาณได้

`lostSec = waitSec + retries × durationSec + durationSec เมื่อ fail` ใช้ชี้ภาระรอ/ทำซ้ำ ไม่ได้ยืนยันว่าเวลานั้นลดได้ทั้งหมด ข้อเสนอจากกฎเป็นสิ่งให้ตรวจ ไม่ใช่การพิสูจน์สาเหตุ

Snapshot แสดงเฉพาะ environment production ของ `operation_runs` ไม่รวม staging/test และไม่แปลง legacy `execution_events` เป็น RUN_LOG โดยเดา field ที่ขาด มีตัวเลขแจ้ง coverage ของ legacy แยกไว้เมื่อมีข้อมูล

Snapshot รองรับสูงสุด 20,000 งาน หากเกินจะคืนข้อผิดพลาดแทนรายงานยอดบางส่วน ทะเบียนรองรับอย่างละ 300 Agent/Skill ต่อ snapshot/การนำเข้าของหน้า ต้องทำบริการรายงานแบบแบ่งหน้าหรือ aggregate เพิ่มเมื่อเกินขอบเขตนี้

## การเชื่อมต่อและความเป็นส่วนตัว

HTML มีเฉพาะ URL และ publishable key ไม่ใช่ service_role/secret key session อยู่ในหน่วยความจำ ไม่เก็บใน localStorage, sessionStorage หรือ IndexedDB รีเฟรชหน้าต้องเข้าสู่ระบบใหม่ ไม่มีการเปิด read access ให้ anon

ข้อมูลโหลดผ่าน API ตรวจ membership และ RLS ทุกครั้ง หน้าอ่านใหม่ประมาณทุก 60 วินาทีเมื่อแท็บมองเห็นและมี session ใช้คำขอที่ไม่ซ้อนกัน การเปลี่ยนตัวกรองไม่สร้าง subscription เพิ่ม การอ่านอัตโนมัตินี้ไม่สั่ง Agent ทำงาน และไม่สร้างข้อมูล

แบบฟอร์มล็อกอินรองรับบัญชีอีเมล/รหัสผ่านที่มีอยู่แล้ว ไม่ได้สร้างกระบวนการ SSO/MFA เต็มชุด Host ที่ยืนยันตัวตนด้วยระบบขององค์กรอยู่แล้วส่ง user access token ผ่าน `window.AgentOps.useAccessToken(token)` ได้ ห้ามส่ง service credentials ไปยัง browser

เมื่ออ่าน/เขียนล้มเหลวจะแจ้งข้อผิดพลาดและไม่อ้างว่า sync สำเร็จ การเขียนหลาย batch อาจสำเร็จบางส่วนแล้ว ควรอ่านกลับและส่งซ้ำด้วย runId เดิมที่ข้อมูลตรงกัน ไม่สร้าง ID ใหม่เพื่อหลบปัญหา

ปุ่ม AI ยังไม่เชื่อมโมเดล ส่งสรุปได้เมื่อ host ต่อ sample adapter และมีงานจริงเท่านั้น ไม่มีการส่งข้อมูลไปยังผู้ให้บริการ AI อัตโนมัติ

## การทดสอบที่ทำจริง

ทดสอบหน้าจอและเงื่อนไขข้อมูลว่าง **49/49 กรณี** ด้วย Chromium/Playwright โดยดักทุก network request ไว้ในเครื่อง ใช้ทะเบียนและประวัติว่าง ทดสอบสถานะสิทธิ์และความล้มเหลว ไม่สร้างข้อมูล Agent/Skill/งานจำลอง ผลอยู่ใน `tests/test-report.json`

ตรวจฐานจริงด้วย SQL: ตารางที่เกี่ยวข้องเปิด RLS, 3 RPC เป็น security invoker และ anon ไม่มีสิทธิ์ execute ทดสอบ role ที่ไม่ทราบตัวตนและ anon แล้วถูกปฏิเสธตามที่คาด โดยไม่เพิ่มแถวทดสอบ คำสั่งอยู่ใน `sql/access-checks.sql`

ยังไม่ได้ทดสอบ real-account login, real RUN_LOG write, การใช้งานพร้อมกันหลายบัญชี, สิทธิ์ SSO/MFA ขององค์กร หรือการเชื่อม runtime จริง การผ่าน local tests ไม่ใช่การรับรองระบบ production แบบครบวงจร

รัน local tests ใน Linux ที่มี Python, Playwright และ `/usr/bin/chromium`:

```bash
python tests/test_real_only.py
```

## ผล security advisor ของโครงการร่วม

ตรวจวันที่ 19 กันยายน 2026 เวลา 19:13 น. ประเทศไทย ไม่พบรายการแจ้งเตือนที่อ้างถึงตาราง/3 RPC ของ Agent Operations ชุดใหม่นี้ในผลที่คืนมา แต่ **โครงการ Supabase โดยรวมยังมีคำเตือนอื่น** ไม่ใช่สถานะปลอดภัยทั้งหมด:

มีฟังก์ชันระบบอื่นที่ search_path เปลี่ยนได้, ฟังก์ชัน SECURITY DEFINER ที่ anon/authenticated เรียกได้, extension citext อยู่ใน public และ Auth ยังไม่ได้เปิด leaked-password protection รวมทั้งข้อมูลแจ้งเตือน dl_config ที่ไม่มี RLS policy บางรายการอาจเป็นการตั้งใจเปิดใช้ ต้องประเมินสิทธิ์จริงแยกต่างหาก ไม่สรุปว่าเป็นช่องโหว่ที่ถูกใช้ได้จากชื่อ lint อย่างเดียว

ไม่ได้ปรับระบบ HR/RHS/DL/Calendar หรือค่า Auth ทั้งโครงการโดยอัตโนมัติ เพราะอยู่นอกขอบเขตงานนี้ แนวทางตรวจต่อ: [search_path](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable), [anon SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [authenticated SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
